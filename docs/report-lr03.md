## Власна реалізація і межі (усі рівні та позначені доповнення)

DTO boundary: реєстрація використовує RegistrationInput; у RegistrationResponse повертаються лише Id, UserName і DisplayName. Паролі, хеші та службові поля Identity не повертаються. CreateIncidentRequest не містить OwnerUserId, Id або Status.

Джерело UserId: GET /api/me і POST /api/incidents отримують ідентифікатор користувача з перевіреного HttpContext.User через ClaimTypes.NameIdentifier. POST /api/incidents захищено RequireAuthorization. Переданий клієнтом ownerUserId ігнорується.

Перевірка пароля: UserManager.CreateAsync застосовує політику складності та хешування ASP.NET Core Identity. SignInManager.PasswordSignInAsync перевіряє пароль стандартним механізмом Identity без порівняння відкритих паролів.

Cookie options: HttpOnly=true, SameSite=Lax; SecurePolicy=SameAsRequest у Development, Always в інших середовищах. На локальному HTTP прапорець Secure відсутній. Строк дії cookie залишено стандартним. SameSite=Lax не замінює CSRF-захисту.

Login-відмови: для неправильних облікових даних і порожніх обов'язкових полів передбачено однаковий HTTP 401 Unauthorized без уточнення причини.

Маршрут довіри: браузер → cookie → middleware автентифікації → авторизація → перевірений principal → endpoint → EF Core → PostgreSQL. Клієнтський UserId або X-Demo-UserId не підтверджує особу користувача.

CSRF-борг: повноцінний захист від CSRF для операцій зміни даних не реалізовано; це залишкове обмеження навчального застосунку.

Перебір облікових записів: потенційні точки — POST /api/auth/login і POST /api/auth/register. Узагальнені відповіді зменшують розкриття інформації про облікові записи, але не запобігають масовим спробам. Rate limiting потрібен для виробничого використання.
