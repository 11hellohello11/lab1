## 2. Контракт і CP-01

Для створення інциденту використано окремий `CreateIncidentRequest`, який містить лише поля `Title`, `Description`, `Severity` та `OccurredAtUtc`. Поля `Id`, `OwnerUserId`, `Status`, `CreatedAtUtc` і `UpdatedAtUtc` не входять до request DTO та встановлюються сервером. Для відповіді використано окремий `CreatedIncidentResponse`, тому сутність бази даних безпосередньо клієнту не серіалізується.

На сервері реалізовано перевірку обов'язковості `title` і `description` після `Trim()`. Максимальна довжина початкового значення `title` становить 160 символів, а `description` — 4000 символів. `severity` перевіряється за допомогою `Enum.TryParse(..., ignoreCase: true)` разом з `Enum.IsDefined`, тому числове значення `"7"` не приймається як допустиме значення enum. Перевірка T-02 з `severity: "7"` завершилася відповіддю `400 Bad Request` з помилкою для ключа `severity`.

Поле `occurredAtUtc` є обов'язковим і не може містити момент часу більш ніж на 5 хвилин у майбутньому. Поточний UTC-час фіксується один раз на початку обробки запиту, а перед збереженням `OccurredAtUtc` нормалізується методом `ToUniversalTime()`. Помилки валідації накопичуються та повертаються через `ValidationProblem` до створення сутності та звернення до бази даних.

Для рівня «Добре» додано міжпольове правило: для `High` і `Critical` нормалізований `description` повинен містити не менше 40 символів. У T-09 опис довжиною 39 символів повернув `400` з помилкою `description`, а опис довжиною 40 символів успішно пройшов перевірку та повернув `201 Created`.

Також реалізовано перевірку конфлікту активного інциденту за нормалізованим `title`. Повторне створення інциденту з тією самою назвою перевірено в T-03 та завершилося `409 Conflict`.

У CP-01 додатково виконано перевірку overposting. До коректного POST-запиту були навмисно додані поля `id`, `ownerUserId` і `status: "Closed"`. Сервер проігнорував ці поля: створеному запису було призначено новий серверний `id`, статус `New`, а після GET створеного інциденту власником відображалася «Аліса Коваль». Отже, клієнт не може встановити server-managed поля через `CreateIncidentRequest`.

## 3. Security-сценарій і CP-02/CP-03

Для дослідження SQL injection було окремо зафіксовано вразливий стан застосунку в commit `b643742`. У цьому стані endpoint `GET /api/incidents/search` формував SQL-запит у `Lab02Endpoints.cs` шляхом конкатенації параметра `q` із текстом SQL, після чого сформований рядок передавався до `FromSqlRaw`. Таким чином, дані з query string змішувалися зі структурою SQL-запиту.

У S-01 на локальній навчальній базі даних було виконано дозволений read-only контрольний запит із підготовленим SQLi-вводом. Сервер повернув `200 OK` та всі 5 штучних seed-записів замість результатів, які відповідали б буквальному пошуковому значенню. Це підтвердило, що введені символи інтерпретувалися як частина SQL-структури. Небезпечні операції зміни або видалення даних не виконувалися.

Першопричиною була не наявність окремого апострофа чи конструкції `OR` сама по собі, а формування SQL-тексту шляхом конкатенації недовіреного значення `q`. Тому фільтрація лише окремих символів або ключових слів не усуває механізм уразливості.

Виправлення зафіксовано окремим commit `f269840`. Пошук переписано з `FromSqlRaw` на LINQ із `EF.Functions.ILike`. Для пошуку формується `pattern`, значення якого EF Core передає параметризовано, тому введення користувача більше не приєднується до структури SQL через конкатенацію. Символи `%`, `_` і `\`, що мають спеціальне значення для `LIKE`, попередньо екрануються, а `\` використовується як escape character. Параметр `sortBy` перевіряється серверним allowlist: дозволено лише `createdAtUtc`, `severity` та `status`, а невідоме значення повертає `400 Bad Request`.

У CP-03 було перевірено diff між commits `b643742` і `f269840`. У vulnerable-версії СУБД отримувала SQL-текст, сформований після конкатенації з `q` та переданий через `FromSqlRaw`, тоді як у fixed-версії пошук реалізовано через LINQ із `EF.Functions.ILike`, де значення `pattern` передається параметризовано, а допустиму структуру сортування визначає серверний allowlist.

Після виправлення повторено початковий контрольний сценарій S-02 з тим самим SQLi-вводом. Endpoint повернув `200 OK` і порожній масив `[]`, тобто введення більше не змінювало логіку SQL-запиту. Позитивну регресію також перевірено пошуком `O'Brien`: запит успішно повернув відповідний запис `O'Brien classroom report`. Невідоме значення `sortBy=abracadabra` повернуло `400 Bad Request` з помилкою для ключа `sortBy`.

## 5. Обмеження і висновок

Під час виконання лабораторної роботи було реалізовано серверну валідацію даних для створення інцидентів, розмежовано request і response DTO та забезпечено серверне встановлення `Id`, власника, статусу й часових полів. Перевірено обов'язковість і максимальну довжину полів, допустимі значення `severity`, обмеження для `occurredAtUtc`, правило 39/40 символів для `High` і `Critical`, конфлікт активних інцидентів з однаковим нормалізованим `title` та відповідь `404` для неіснуючого запису.

У vulnerable commit `b643742` було відтворено SQL injection у локальному read-only сценарії та встановлено його першопричину — конкатенацію недовіреного параметра `q` із текстом SQL перед виконанням через `FromSqlRaw`. У fixed commit `f269840` першопричину усунено: пошук переписано на LINQ із `EF.Functions.ILike`, значення пошукового шаблону передається параметризовано, спеціальні символи шаблону екрануються, а `sortBy` обмежується серверним allowlist. Повторний S-02 з тим самим контрольним вводом повернув `200 OK` і `[]`, а пошук легітимного значення з апострофом залишився працездатним.

Під час A-01 у fixed state знайдено одне місце використання raw-SQL API: `ExecuteSqlRawAsync` у `DatabaseBootstrap.cs`, яке виконує статичний службовий `TRUNCATE` і не містить даних користувача. У `Lab02Endpoints.cs` raw SQL після виправлення відсутній, а пошук реалізовано через LINQ із `EF.Functions.ILike`. Додатково автоматичні тести T-02 і T-03 пройшли успішно; загальний результат тестування становить 7 успішних тестів із 7.

Поточна перевірка конфлікту `title` виконується через попередній `AnyAsync`. Вона достатня для навчального сценарію, однак не гарантує атомарність за одночасного виконання кількох запитів: два паралельні запити теоретично можуть пройти перевірку до збереження одного з них. Для усунення такого race condition у виробничій системі потрібне обмеження унікальності або інший механізм забезпечення цілісності на рівні бази даних. Під час виконаних перевірок помилок читання JSON не спостерігалося.
