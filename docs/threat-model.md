## Схема меж довіри

```text
[Користувач / Browser client]
              |
              | HTTP, cookie, JSON
              v
========== Межа довіри 1 ==========
              |
      [ASP.NET Core API]
       - Authentication
       - Authorization
       - Validation
       - Incident endpoints
              |
              | EF Core / Npgsql
              v
========== Межа довіри 2 ==========
              |
    [PostgreSQL / Docker Compose]


         [Git repository]
              |
========== Межа довіри 3 ==========
              v
       [Restore / Build]


    [Змінні середовища]
              |
========== Межа довіри 4 ==========
              v
    [Конфігурація застосунку]
```

Межа довіри 1 — браузер надсилає HTTP-запити, параметри яких можуть бути змінені незалежно від клієнтського інтерфейсу. Тому сервер виконує перевірку автентифікації, авторизації та допустимості операцій.

Межа довіри 2 — API взаємодіє з PostgreSQL через EF Core/Npgsql. Захист передбачає безпечне формування SQL-запитів і контроль доступу до записів інцидентів.

Межа довіри 3 — вихідні файли репозиторію та залежності використовуються під час відновлення пакетів і збірки. Необхідно перевіряти відстежувані Git-файли на наявність секретів.

Межа довіри 4 — застосунок отримує конфігураційні значення зі змінних середовища та локальних конфігураційних файлів. Секрети не повинні потрапляти до Git, HTTP-відповідей або діагностичних журналів.

## Очікувані властивості на межах

| Межа | Очікувана властивість (усі рівні) | Конкретний test або перевірка (добрий і відмінний) |
|---|---|---|
| browser→API | Сервер перевіряє вхідні параметри, автентифікацію та права доступу. Для змінювальних запитів, які використовують authentication cookie, потрібна antiforgery validation. Недовірений текст не повинен виконуватися як HTML або JavaScript. | Перевірки SQLi, authentication, authorization/IDOR, XSS і CSRF у regression pack достатнього рівня. |
| API→PostgreSQL | SQL-запити не повинні допускати ін'єкцій, а доступ до інцидентів має обмежуватися правами користувача та належністю ресурсу. | Повторна перевірка SQLi та IDOR. |
| repository→build | Відстежувані файли Git не повинні містити реальних паролів, токенів або ключів. Відновлення залежностей має бути відтворюваним. | Перевірка tracked files і `dotnet restore --locked-mode`. |
| environment→configuration | Секрети передаються поза Git. Production-like відповіді не розкривають stack trace, SQL, connection string або локальні шляхи. | Перевірка безпечної обробки помилок і trace identifier на етапі 1. |

## Обмеження висновків

Модель описує локальний навчальний стенд SecureLab на початку ЛР 6. Вона не підтверджує відсутність усіх можливих вразливостей. Результати перевірки механізмів захисту та залишкові ризики будуть зафіксовані в `docs/security-review.md`.
