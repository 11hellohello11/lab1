# Звіт ЛР04


## Контекст і межа виконання

Рівень виконання: достатній («Задовільно»).

Роботу виконано на основі лабораторної роботи №3, базовий тег — v0.3.0.

Головна захищена операція: GET /api/incidents/{id}.

Обрана політика відмови:
- 401 Unauthorized — для неавтентифікованого користувача;
- 404 Not Found — для автентифікованого користувача без права доступу до інциденту.

Для ролі Reporter дозволено перегляд власних інцидентів.
Для ролі Analyst дозволено перегляд інцидентів з метою аналізу.

Маршрут GET /api/incidents/{id} захищено відповідно до вимог достатнього рівня. Операція створення інциденту успадкована з ЛР3.

Додаткові завдання доброго та відмінного рівнів не виконувалися.


## Матриця і server-side рішення

Матрицю прав доступу наведено у файлі docs/access-matrix.md.

Для маршруту GET /api/incidents/{id} реалізовано обов'язкову автентифікацію через RequireAuthorization().

Ідентифікатор поточного користувача отримується із перевіреного HttpContext.User за ClaimTypes.NameIdentifier. Роль Analyst перевіряється за допомогою IsInRole().

У методі IncidentQueries.GetDetailsAsync застосовано query scoping: інцидент вибирається лише за умови збігу його власника з поточним користувачем або наявності дозволеної ролі Analyst.

Якщо доступ до інциденту відсутній, сервер повертає 404 Not Found без даних ресурсу. Це дозволяє не повідомляти сторонньому користувачеві, чи існує запитаний інцидент.

Ідентифікатор власника та роль не приймаються з клієнтських параметрів запиту. Для читання використовується наявний IncidentDetailsResponse, який не містить внутрішніх полів ownerUserId та email.

Окремий resource-based authorization handler не створювався, оскільки для достатнього рівня використано серверне обмеження вибірки.


## Вразливий стан і PoC

Головна операція: GET /api/incidents/{id}.

Вразливість: IDOR/BOLA — несанкціоноване читання чужого інциденту.

У початковому стані ЛР3 метод IncidentQueries.GetDetailsAsync виконує вибірку за умовою:

.Where(incident => incident.Id == id)

При цьому не перевіряється OwnerUserId та роль поточного користувача. Маршрут GetIncidentDetails також не вимагає автентифікації.

## Основний finding і залишковий ризик (усі рівні)

Під час дослідження маршруту GET /api/incidents/{id} виявлено вразливість IDOR/BOLA, яка дозволяла користувачеві Alice з роллю Reporter отримувати інформацію про інцидент Bob шляхом підміни ідентифікатора ресурсу.

У початковому стані сервер повертав 200 OK для чужого інциденту. Причиною була вибірка даних лише за incident.Id без перевірки власника та ролі поточного користувача.

Вразливий стан зафіксовано комітом:
a695a37a9f8fe128783ca145db3f0af33ace0ab3

Для усунення вразливості додано обов'язкову автентифікацію маршруту та перевірку прав доступу на рівні запиту до бази даних.

Після виправлення запит Alice до інциденту Bob повертає 404 Not Found, тоді як читання власного інциденту Alice та аналітичний перегляд Morgan завершуються відповіддю 200 OK.

Проведено автоматизоване тестування: усі 14 тестів завершилися успішно.

Залишковий ризик: у межах достатнього рівня захищено вибрану операцію читання деталей інциденту. Окреме обмеження доступу до загального списку, пошуку, статистики та непрямих маршрутів належить до розширених рівнів виконання. Захист від CSRF для змінювальних операцій із cookie-автентифікацією залишається навчальним завданням наступних лабораторних робіт.


## Browser flow (усі рівні)

Перевірку виконано в браузері після автентифікації користувача Alice через сторінку auth-lab.html.

Під час відкриття власного інциденту «Підозрілий лист із вкладенням» браузерний клієнт успішно відобразив його назву, опис, статус, критичність, власника та коментарі.

Для перевірки забороненого доступу використано навчальний сценарій:

loadIncidentDetails("20000000-0000-0000-0000-000000000002");

Сервер повернув 404 Not Found, а браузер відобразив повідомлення «Помилка: Інцидент не знайдено».

У файлі Client/app.js для відображення даних і повідомлень використано textContent та createTextNode(), без використання innerHTML.

Таким чином, браузерний клієнт правильно відображає дозволений результат і серверну відмову, не виконуючи отриманий текст як HTML.
